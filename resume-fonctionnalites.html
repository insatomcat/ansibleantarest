Déploiement Ansible d'Antares-Web + Slurm

Playbook ansibleantarest : d'une VM nue à une instance Antares-Web exploitable en une commande, cluster de calcul compris.

Un playbook Ansible qui déploie Antares-Web (AntaREST) et, en option, un cluster Slurm complet, sur Debian / Ubuntu comme sur les rebuilds RHEL. Conteneurs podman + quadlet, TLS, durcissement, build d'artefacts réutilisables et playbook de vérification post-déploiement.

Architecture déployée

antares_webBuild et exécution d'Antares-Web (podman + quadlet, TLS optionnel)
slurm_frontendContrôleur Slurm, base de comptabilité, serveur NFS pour /home
slurm_computeNœuds de calcul, montage du /home partagé

Une même machine peut cumuler plusieurs groupes. Slurm est facultatif : slurm_enabled: false donne un Antares-Web seul avec solveur local. Le nombre de nœuds vient de l'inventaire, slurm.conf étant généré depuis les facts.

Conteneurs et exploitation

Ni Docker ni compose.

Chaque conteneur est une unité quadlet systemd (antarest, celery-beat, celery-worker, postgresql, redis, antares-nginx), regroupée sous une antares-web.target qui remplace compose up/down.

Redémarrage maîtrisé.

Restart=on-failure avec budget systemd : un conteneur qui boucle finit en failed, visible dans systemctl --failed, plutôt que de redémarrer indéfiniment.

Podman rootful.

Le rootless remapperait les UID et casserait la cohérence de propriété des fichiers avec le /home NFS.

Multi-distribution, vérifié en CI

Tout passe par ansible.builtin.package ; les différences (CRB/EPEL, noms de paquets, OpenHPC pour Slurm sur EL) sont résolues en un seul endroit par rôle. Chaque distribution est déployée à chaque PR, en machine seule et en cluster de cinq VM.

Solveurs et Antares-Xpansion

Binaires Antares Simulator.

Séries 8.8.x et 9.2.x, avec choix automatique du build selon la glibc de la famille (Ubuntu 22.04 ou Oracle Linux 8).

Xpansion en option.

Implémentation C++, runtime MPI sur les nœuds, déployé uniquement sur le cluster puisque le launcher local d'Antares-Web ignore le mode Xpansion.

Script de lancement corrigé.

launchAntares.sh sort sur le code de retour du run : un solveur tué par l'OOM killer remonte en rouge au lieu d'un faux vert, après le post-traitement et le zip.

Limites assumées

  • Xpansion en C++ uniquement, et sur cluster seulement.
  • Le firewall filtre l'hôte, pas le trafic conteneur : les PublishPort font foi.
  • La jail du formulaire de login bannit à l'adresse IP (10 échecs en 10 min) : une attaque répartie sur beaucoup d'adresses passe sous le seuil.
  • EL 8, Debian 12 et Ubuntu 22.04 exclus : podman trop ancien pour quadlet.
  • RHEL listé sur la foi de ses rebuilds, faute d'abonnement en CI.

TLS et tâches de fond

TLS intégré.

Le nginx déjà présent termine le TLS : Let's Encrypt (certbot, http-01 servi par le stack lui-même), auto-signé ou certificat fourni. Premier run en une seule passe, HSTS et redirection incluses.

Le mécanisme de fond actuel.

Les tâches périodiques tournent dans celery-beat et celery-worker, le schéma que le projet privilégie aujourd'hui, et non dans les conteneurs watcher / matrix_gc qui sont en voie d'obsolescence. Neuf tâches couvertes au lieu de deux.

Ménage en marche à blanc.

Les collecteurs et l'archiveur démarrent en journalisant ce qu'ils supprimeraient, sans rien supprimer. L'exploitant lit quelques cycles dans journalctl -u antarest-celery-worker, vérifie que la liste est celle qu'il attend, puis les autorise un par un à supprimer pour de bon.

Durcissement

Le rôle hardening s'exécute tôt, avant tout déploiement, en quatre blocs indépendants :

  • nftables dans une table dédiée, sans toucher au hook forward ni à /etc/nftables.conf.
  • fail2ban : jail sshd et jail sur le formulaire de login Antares, bans posés en prerouting car un ban en input ne voit pas le trafic DNATé vers les conteneurs.
  • sshd sans mot de passe, avec contrôle préalable des clés autorisées et sshd -t avant application.
  • Mises à jour de sécurité automatiques, sans reboot : une étude tourne parfois des heures.

Le rôle signale aussi les secrets restés à leur valeur d'exemple, et peut refuser de déployer dans ce cas.

Build once, deploy everywhere

build.yml produit sur une machine de build les artefacts dans ./artifacts : image backend (UID gravé), images tierces, frontend, tarballs solveurs et manifest.yml. Les cibles se déploient ensuite sans npm ni build, les archives étant transportées en rsync. Le playbook de build réutilise les mêmes fichiers de tâches que le déploiement, donc les artefacts ne peuvent pas être produits par une autre recette.

Vérification post-déploiement

verify.yml contrôle ce que site.yml ne peut pas voir depuis une seule machine, sans rien modifier :

  • slurmctld vivant et voyant tous les nœuds de l'inventaire, cluster enregistré en comptabilité ;
  • montage NFS réellement effectif : marqueur écrit d'un côté, lu de l'autre ;
  • job soumis exactement comme le backend le fait, en SSH avec la clé générée ;
  • les trois rulesets firewall, vus des deux côtés.
